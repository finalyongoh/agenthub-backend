# AgentHub 시스템 정의서

## 1. 문서 개요

### 1.1 문서 목적

본 문서는 AgentHub가 해결하려는 문제, 시스템의 목표, 대상 사용자, 핵심 범위 및 MVP 방향성을 정의하기 위한 시스템 정의 문서입니다.

이 문서는 이후 요구사항정의서, 유즈케이스, 기술 설계의 기준이 되는 상위 방향성을 제공합니다.

세부 구현 방식, API 호출 전략, 데이터 구조, 점수 산식 등의 기술 스펙은 후속 기술 설계 단계에서 구체화합니다. 다만 커뮤니티 기능, 데이터 수집, AI 분석의 기본 원칙과 사용자 역할, 데이터 갱신 및 예외 대응의 핵심 기획 범위는 본 문서에서 명세합니다.

### 1.2 시스템명

**AgentHub**

### 1.3 한 줄 정의

AgentHub는 개인 개발자가 빠르게 변화하는 AI Agent 기술 생태계를 따라가기 위해, Agent/MCP/Skill/Eval 관련 GitHub 오픈소스 프로젝트를 수집·분석하고, AI 기반 분석 결과와 커뮤니티 신호를 함께 제공하는 기술 탐색 커뮤니티 서비스이다.

---

## 2. 배경과 문제 정의

AI Agent 생태계는 빠르게 변화하고 있으며, GitHub에는 Agent Framework, Coding Agent, MCP Server, Skill, Eval Harness, Tool-use Framework 등 다양한 프로젝트가 지속적으로 등장하고 있다.

기존 GitHub Trending이나 star 기반 탐색 방식은 다음과 같은 한계를 가진다.

1. 어떤 저장소가 인기 있는지는 보여주지만, Agent Engineering 관점에서 왜 중요한지는 설명하지 않는다.
2. README의 주장과 실제 구현 근거를 구분하지 않는다.
3. MCP, Skill, Tool-use, Eval/Harness, Risk 같은 Agent 특화 분석 축을 제공하지 않는다.
4. 개인 개발자가 팔로우업하려면 어디부터 봐야 하는지 안내하지 않는다.
5. 커뮤니티에서 실제로 어떤 repo를 읽고, 실행해보고, 비교했는지에 대한 신호가 분리되어 있지 않다.

따라서 AgentHub는 단순 인기 순위가 아니라, **Agent 기술 흐름을 빠르게 파악하고 팔로우업을 쉽게 시작할 수 있도록 돕는 시스템**을 목표로 한다.

---

## 3. 시스템 목표

### 3.1 핵심 목표

AgentHub의 핵심 목표는 다음과 같다.

> 개인 개발자가 AI Agent 기술 흐름을 파악하고 팔로우업 대상을 선정하는 데 드는 시간을 줄인다.
> 

이를 위해 시스템은 GitHub 기반 Agent 관련 프로젝트를 수집하고, 각 repo에 대해 기술적 맥락과 팔로우업에 필요한 정보를 구조화하여 제공한다.

### 3.2 세부 목표

1. Agent/MCP/Skill/Eval 관련 GitHub repo를 지속적으로 수집한다.
2. repo의 README Claim과 구현 근거를 구분하여 보여준다.
3. Agent Engineering 관점의 유형, 구현 신호, 위험 신호를 요약한다.
4. 사용자가 어떤 repo 또는 기술 흐름을 팔로우업해야 할지 판단할 수 있게 돕는다.
5. 사용자가 팔로우업을 시작할 때 어디부터 보면 되는지 안내한다.
6. 개발자 커뮤니티가 repo에 대한 경험, 판단, 보완 정보를 축적할 수 있게 한다.
7. AI 기반 분석 결과와 커뮤니티 신호를 분리하여 제공한다.

## 4. 핵심 사용자

### 4.1 1차 사용자

AgentHub의 1차 사용자는 **개인 개발자**이다.

이 사용자는 다음과 같은 상황에 있다.

- AI Agent 기술 흐름을 따라가고 싶다.
- GitHub에 새로 올라오는 Agent 관련 repo를 직접 모두 확인하기 어렵다.
- README만 보고는 실제 구현 근거를 판단하기 어렵다.
- MCP, Skill, Eval, Tool-use 같은 흐름을 놓치고 싶지 않다.
- 어떤 repo부터 읽고 실험해야 할지 빠르게 판단하고 싶다.
- 다른 개발자들이 어떤 repo를 보고 있는지도 참고하고 싶다.

### 4.2 향후 확장 사용자

향후에는 다음 사용자를 추가로 고려할 수 있다.

- Agent Framework를 비교하려는 개발자
- 특정 MCP Server 또는 Skill 구조를 참고하려는 개발자
- Agent 프로젝트의 기술 동향을 모니터링하려는 팀
- 오픈소스 Agent 생태계를 관찰하려는 리서처
- 커뮤니티 기반 기술 큐레이션에 참여하려는 개발자

단, 초기 시스템 정의에서 최우선 사용자는 개인 개발자로 둔다.

### 4.3 사용자 역할과 권한

AgentHub의 사용자는 최소한 다음 역할로 구분한다.

- **비로그인 사용자:** 레포지토리 카드, Period / 주간 탐색 리포트, 팔로우업 목록 등 공개 정보를 조회할 수 있다.
- **로그인 사용자:** 북마크, 읽음 처리, 댓글, 반응, 사용 후기, 구현 근거 보완 제안, 분석 오류 제보 등 커뮤니티 피드백을 생성할 수 있다.
- **관리자:** 부적절한 커뮤니티 신호를 숨김 또는 삭제하고, 잘못된 레포지토리 카드를 숨김 처리하거나 재분석을 요청할 수 있다.

초기 인증 방식은 GitHub 기반 개발자 커뮤니티라는 제품 성격을 고려하여 GitHub OAuth를 우선 후보로 둔다. 단, 최종 인증 제공자, 세부 권한 모델, 세션 관리 방식은 기술 설계 단계에서 확정한다.

## 5. 제품 정체성

AgentHub는 다음 성격을 가진다.

### 5.1 기술 탐색

이 시스템은 특정 repo 하나를 깊게 감사하는 도구가 아니라, Agent Engineering 생태계에서 어떤 repo와 기술 흐름이 나타나고 있는지 빠르게 파악하게 해주는 기술 탐색이다.

### 5.2 팔로우업 가이드

이 시스템은 repo를 단순히 나열하지 않는다. 각 repo에 대해 사용자가 후속 탐색을 쉽게 시작할 수 있도록 다음 정보를 제공한다.

- 이 repo가 무엇인지
- 어떤 Agent Engineering 유형인지
- 어떤 Claim을 하고 있는지
- 구현 근거가 어디에 있는지
- 위험 신호가 있는지
- 먼저 어디를 보면 좋은지

### 5.3 커뮤니티 서비스

AgentHub는 AI 분석 결과를 제공하는 기술 탐색이자, 개발자들이 repo에 대한 의견, 사용 경험, 보완 정보, 비교 관점을 함께 남기고 소통하는 커뮤니티 서비스입니다.

단, 커뮤니티 신호는 자동 분석 결과와 분리하여 관리합니다.

### 5.4 독자적인 기술 탐색 정체성

AgentHub는 GitHub Trending처럼 신속한 정보 조회를 지원하며, 'Agent 기술 흐름을 따라가기 위해 무엇을 봐야 하는가'에 대한 선별 정보를 제공하는 것을 지향합니다.

## 7. 핵심 개념 정의

### 7.1 자동 분석 결과

자동 분석 결과는 시스템이 GitHub repo를 기반으로 생성하는 분석 결과이다.

예시는 다음과 같다.

- repo 유형 분류
- README Claim 추출
- 구현 근거 확인
- MCP 관련 신호
- Skill 관련 신호
- Tool-use 관련 신호
- Eval/Harness 관련 신호
- Risk 기본 체크
- 신규 또는 변경 repo 중심의 AI 분석
- 레포지토리 카드 생성
- 팔로우업 가이드 제공

자동 분석 결과는 시스템이 제공하는 구조화된 분석 결과이며, 커뮤니티 반응과 구분된다.

### 7.1.1 구현 근거 확인의 MVP 범위

MVP 단계의 구현 근거 확인은 사용자가 repo를 팔로우업할 때 참고할 수 있는 **구현 근거** 를 제공하는 것을 목표로 한다. 이는 완전한 코드 검증, 런타임 실행, 보안 감사, 모든 언어별 AST 분석을 의미하지 않는다.

본 문서에서 구현 근거는 “검증 완료된 증거”가 아니라, README Claim을 원본 repo에서 후속 확인할 수 있게 돕는 구조적·정적 신호를 의미한다. 따라서 사용자 화면에서는 가능한 한 **구현 근거**, **구현 근거**, **확인 가능한 패턴**처럼 검증 보장을 암시하지 않는 용어로 표현한다.

MVP 단계의 구현 근거 확인은 다음 신호를 중심으로 수행한다.

- README와 문서에 명시된 기능 설명
- repo 메타데이터와 최근 활동 신호
- 주요 파일 및 디렉토리 구조
- `tools/`, `skills/`, `eval/`, `benchmarks/`, `mcp/` 등 Agent Engineering 관련 패턴
- MCP / Skill / Tool-use / Eval / Observability / Guardrail 관련 정적 텍스트 신호
- API 호출, tool definition, eval harness, tracing 설정 등 명시적으로 확인 가능한 코드 또는 설정 파일 신호

따라서 MVP의 구현 근거는 “확정적 검증 결과”가 아니라 “팔로우업할 가치가 있는 구현 근거”로 제공한다. 시스템은 코드의 실행 가능성, 보안성, 성능, 실제 운영 적합성을 보장하지 않으며, 사용자가 실제 채택 여부를 판단하기 위해서는 원본 repo 확인과 추가 검증이 필요하다.

### 7.1.2 분석 결과의 불확실성 상태

자동 분석 결과는 AI 기반 분석을 포함할 수 있으므로 모든 분석 결과가 동일한 확신도를 가지지 않는다. 시스템은 분석 결과를 단정적으로만 제공하지 않고, 필요한 경우 다음과 같은 상태를 구분한다.

- 분석 완료
- 근거 부족
- 분류 불확실
- 분석 실패
- 재분석 필요

분석 실패, 근거 부족, 불확실한 분류 결과는 내부 상태로 저장하며, 사용자 화면에서는 확정 분석 결과와 구분하여 표시한다.

### 7.2 커뮤니티 피드백

커뮤니티 피드백은 사용자가 repo 또는 기술 흐름에 대해 남기는 반응과 경험이다.

예시는 다음과 같다.

- 북마크
- 읽음 표시
- 댓글
- 토론
- 추천 또는 반응
- 사용 후기
- 실제 실행 경험
- 유사 repo 제보
- 분석 오류 제보
- 구현 근거 보완 제안
- 팔로우업 팁

커뮤니티 피드백은 자동 분석 결과를 보완하지만, 초기에는 하나의 점수로 섞지 않는다.

### 7.3 레포지토리 카드

레포지토리 카드는 개별 GitHub repo를 Agent Engineering 관점에서 요약한 카드이다.

레포지토리 카드는 단순 설명 카드가 아니라, 사용자가 repo를 팔로우업하기 쉽게 만드는 단위 정보이다.

### 7.4 팔로우업 목록

팔로우업 목록는 사용자가 이번 기간에 직접 확인해볼 만한 repo 또는 기술 흐름을 모아 보여주는 목록이다.

팔로우업 목록는 단순히 “좋은 repo 순위”가 아니라, Agent 기술 흐름을 따라가기 위해 확인할 가치가 있는 대상을 제시한다.

### 7.5 Period / 주간 탐색 리포트

Period / 주간 탐색 리포트는 특정 기간 동안의 Agent Engineering 흐름을 요약하는 리포트이다.

기본 단위는 Weekly Report가 될 수 있으나, 사용자는 기간을 바꾸어 볼 수 있어야 한다.

## 8. 사용자 경험 개요

### 8.1 기본 사용 흐름

AgentHub의 기본 사용 흐름은 다음과 같다.

1. 사용자는 Trending처럼 빠르게 훑을 수 있는 메인 화면 또는 기간별 탐색 리포트를 본다.
2. 이번 기간의 Agent Engineering 흐름을 파악한다.
3. 팔로우업 목록에서 직접 확인해볼 repo 또는 기술 흐름을 고른다.
4. 레포지토리 카드에서 개별 repo의 Claim, 구현 근거, Risk, 팔로우업 가이드를 확인한다.
5. 필요한 경우 로그인 사용자는 repo를 북마크하거나, 읽음 처리하거나, 커뮤니티 의견을 확인한다.
6. 로그인 사용자는 직접 읽어본 내용이나 실행 경험을 커뮤니티 신호로 남길 수 있다.

### 8.2 메인 경험 방향

메인 경험은 GitHub Trending처럼 빠르게 훑을 수 있어야 한다.

다만 화면의 목적은 인기 repo 나열이 아니라 다음 정보를 함께 제공하는 것이다.

- Agent Engineering 맥락
- 왜 눈에 띄는지
- Claim과 구현 근거
- 팔로우업 시작점
- 커뮤니티 반응

### 8.3 메인 큐레이션 기본 원칙

메인 화면과 Period / 주간 탐색 리포트는 단순 Star 순, 단순 최신순, 단일 점수 순위를 기본 원칙으로 삼지 않는다.

초기 큐레이션은 사용자가 “이번 기간에 무엇을 팔로우업해야 하는가”를 판단할 수 있도록 다음 신호를 분리하여 제공하는 방향을 따른다.

- 최근 수집 또는 최근 변경된 repo
- Agent Engineering 관련성이 높은 repo
- README Claim과 구현 근거 사이의 비교가 가능한 repo
- MCP / Skill / Tool-use / Eval / Observability / Guardrail 등 특정 흐름을 대표하는 repo
- 위험 신호 또는 불확실성이 있어 주의 깊게 볼 필요가 있는 repo
- 커뮤니티에서 보완 정보, 실행 경험, 비교 의견이 쌓이는 repo

구체적인 정렬 기준, 점수 산식, 탐색 랭킹, Follow-up 점수 공식은 시스템 정의서 단계에서 확정하지 않는다. 해당 항목은 실제 데이터와 사용자 반응을 기반으로 PRD 또는 기술 설계 단계에서 결정한다. 단, 향후 큐레이션 및 랭킹 점수 산출 시에는 최근 커밋 주기(활동성), Star 증가율(트렌드 전파 속도), Fork 수 대비 Issue 해결률(유지보수 건강도), 그리고 커뮤니티 피드백 지표(실행 경험 보고 수 등)의 가중치를 종합적으로 반영한다는 정성적 방향성을 기본으로 삼는다.

## 10. 데이터 수집과 제공 방식

### 10.1 GitHub API의 역할

GitHub API는 사용자 요청을 실시간으로 처리하기 위한 API가 아니다.

GitHub API는 Agent Explore Dataset을 만들기 위한 데이터 수집원으로 사용한다.

즉, 시스템 구조는 다음 방향을 가진다.

> GitHub API → 내부 Explore Dataset → 분석 결과 생성 → 사용자에게 제공
> 

사용자가 화면을 볼 때마다 GitHub API를 직접 호출하는 구조는 지양한다.

### 10.2 내부 Explore Dataset

AgentHub는 GitHub에서 수집한 repo 정보와 분석 결과를 내부 데이터셋으로 축적한다.

사용자는 이 데이터셋을 기반으로 생성된 화면, 리포트, 레포지토리 카드, 커뮤니티 정보를 조회한다.

이를 통해 사용자 수 증가가 GitHub API 호출량 증가로 직접 이어지지 않도록 한다.

### 10.3 초기 수집 대상 발견 원칙

AgentHub는 전체 GitHub를 무제한 탐색하는 시스템이 아니다. 초기 수집 대상은 Agent Engineering과 직접 연결될 가능성이 높은 후보군에서 발견하고, 이후 내부 Explore Dataset으로 축적하는 방식을 따른다.

초기 repo 발견은 다음 경로를 조합하여 이루어질 수 있다.

- GitHub topic 또는 키워드 기반 후보 탐색
- Agent / MCP / Skill / Eval / Tool-use 관련 문서, README, 디렉토리 패턴을 가진 repo 탐색
- 이미 수집된 repo의 문서, 예제, dependency, 관련 링크에서 파생되는 후보 탐색
- 로그인 사용자의 repo URL 제보
- 관리자의 후보 repo 등록 또는 제외 처리

다만 구체적인 GitHub 검색 쿼리, topic 목록, 호출 주기, API 예산, 후보 필터링 점수, 중복 제거 방식은 기술 설계 단계에서 확정한다. 시스템 정의서 단계에서는 “무엇을 최초 수집망에 올릴 수 있는가”에 대한 원칙만 정의한다.

### 10.4 데이터 갱신 원칙

AgentHub의 데이터 수집은 사용자 요청마다 GitHub API를 직접 호출하는 방식이 아니라, 내부 Explore Dataset을 구축하고 갱신하는 정기적 수집 흐름을 기본으로 한다.

데이터 갱신은 다음 원칙을 따른다.

- 신규 repo 발견과 기존 repo 갱신을 구분한다.
- 이미 수집된 repo는 변경이 감지된 경우 우선적으로 갱신한다.
- 전체 재수집보다 증분 갱신을 우선한다.
- GitHub API Rate Limit과 수집 비용을 고려하여 수집량을 통제한다.
- 구체적인 실행 주기, API 호출량, 재시도 정책, SLA는 기술 설계 단계에서 확정한다.

이 원칙을 통해 사용자 수 증가가 GitHub API 호출량 증가로 직접 이어지지 않도록 한다.

### 10.5 AI 분석 비용 및 실패 통제 원칙

자동 분석 결과는 AI 기반 Claim 추출, 구현 근거 요약, 위험 신호 요약을 포함할 수 있다. 따라서 시스템은 분석 비용과 품질 리스크를 통제해야 한다.

AI 분석은 다음 원칙을 따른다.

- 모든 repo를 매번 전체 재분석하지 않는다.
- 신규 repo 또는 변경이 감지된 repo를 우선 분석한다.
- README, 주요 문서, 제한된 코드/설정 파일 등 분석 대상 범위를 통제한다.
- 분석 실패 시 실패 상태와 원인을 저장한다.
- 근거가 부족하거나 불확실한 분석은 확정 결과처럼 표시하지 않는다.
- 토큰 예산, 모델 선택, 재시도 정책, 프롬프트 구조는 기술 설계 단계에서 확정한다.

>

- Agent 관련 GitHub repo 수집
- repo 메타데이터 수집
- README Claim 추출
- 주요 구현 근거 확인
- 구현 근거 확인 범위와 분석 불확실성 상태 표시

- MCP / Skill / Tool-use / Eval 여부 감지

- 신규 또는 변경 repo 중심의 AI 분석

- 최소 커뮤니티 신호 기능
- 비로그인/로그인/관리자 역할 구분
- 관심 레포 변경 알림 기능 (북마크한 레포의 업데이트, release 등 감지 및 알림)
- 자유게시판 기능 (AI/Agent 관련 자유 주제의 게시글 및 댓글 작성)

- 검증되지 않은 복잡한 점수 산식

## 12. 커뮤니티 기능의 시스템 내 위치

커뮤니티 기능은 선택적 부가기능이 아니라 시스템의 필수 구성 요소이다.

다만 커뮤니티 신호는 자동 분석 결과와 구분하여 관리한다.

### 12.1 커뮤니티 기능의 목적

커뮤니티 기능의 목적은 다음과 같다.

1. AI 분석이 놓친 정보를 보완한다.
2. 실제 사용 경험을 축적한다.
3. repo별 후속 탐색 팁을 공유한다.
4. 유사 repo나 비교 대상을 제보한다.
5. Agent 기술 흐름에 대한 개발자 집단 신호를 만든다.
6. AI/Agent 관련 자유로운 지식 공유 및 개발자 간 네트워킹을 지원한다 (자유게시판).

### 12.2 분리 원칙

자동 분석 결과와 커뮤니티 피드백은 별도의 정보로 제공한다.

예를 들어 하나의 레포지토리 카드 안에서도 다음과 같이 구분한다.

- 시스템 분석 결과
- 커뮤니티 반응
- 사용자 후기
- 보완 제안

초기 단계에서는 두 신호를 하나의 단일 점수로 합치지 않는다.

자유게시판 기능은 특정 레포에 한정되지 않는 범용 커뮤니티 공간으로 제공되며, 레포지토리 중심의 커뮤니티 피드백과는 별도의 독립적인 영역으로 서비스한다.

### 12.3 커뮤니티 신호 생성 권한

커뮤니티 신호는 서비스 신뢰도에 직접 영향을 줄 수 있으므로 생성 주체를 식별할 수 있어야 한다.

- 비로그인 사용자는 공개된 커뮤니티 신호를 조회할 수 있다.
- 로그인 사용자는 북마크, 읽음 처리, 댓글, 반응, 사용 후기, 구현 근거 보완 제안, 분석 오류 제보를 생성할 수 있다.
- 로그인 사용자가 생성한 커뮤니티 신호는 자동 분석 결과와 분리하여 저장하고 제공한다.

### 12.4 어뷰징 대응 원칙

커뮤니티 피드백은 개발자 집단 신호를 만들기 위한 기능이지만, 스팸, 도배, 허위 제보, 광고성 댓글, 부적절한 반응이 발생할 수 있다.

시스템은 다음 운영 원칙을 가진다.

- 부적절한 커뮤니티 신호는 숨김 또는 삭제 대상이 될 수 있다.
- 반복적인 어뷰징 사용자는 기능 제한 대상이 될 수 있다.
- 분석 오류 제보와 구현 근거 보완 제안은 원본 자동 분석 결과를 즉시 덮어쓰지 않고, 별도 신호로 관리한다.
- 커뮤니티 신호를 분석 점수나 정렬 기준에 반영하는 방식은 초기 단계에서 확정하지 않는다.

### 12.5 분석 오류 제보와 재분석 피드백 루프

분석 오류 제보와 구현 근거 보완 제안은 자동 분석 결과의 신뢰도를 높이기 위한 입력으로 사용될 수 있다. 다만 커뮤니티 제보는 원본 분석 결과를 자동으로 덮어쓰지 않는다.

시스템은 다음 원칙을 따른다.

- 분석 오류 제보와 구현 근거 보완 제안은 자동 분석 결과와 분리된 커뮤니티 피드백로 저장한다.
- 동일 repo에 대해 유의미한 제보가 누적되거나 관리자가 제보를 승인한 경우, 해당 repo는 재분석 필요 상태로 전환될 수 있다.
- 재분석 결과는 기존 분석 결과를 무조건 대체하지 않고, 갱신 이력과 분석 상태를 함께 관리하는 방향을 따른다.
- 명백히 잘못된 레포지토리 카드는 관리자가 숨김 처리하거나 재분석을 요청할 수 있다.
- 커뮤니티 제보를 AI 분석에 자동 학습시키거나 즉시 정답으로 반영하는 방식은 초기 단계에서 적용하지 않는다.

### 12.6 관리자 역할

관리자는 시스템의 분석 결과와 커뮤니티 신호가 서비스 품질을 해치지 않도록 최소한의 운영 권한을 가진다.

관리자 역할은 다음을 포함한다.

- 부적절한 댓글, 반응, 제보의 숨김 또는 삭제
- 잘못된 레포지토리 카드의 숨김 처리
- 특정 repo에 대한 재분석 요청
- 명백히 범위 밖인 repo의 제외 처리
- 반복적인 어뷰징 사용자에 대한 제한 처리

관리자 기능의 상세 UI, 운영 워크플로우, 감사 로그, 제재 정책은 운영 정책 또는 기술 설계 단계에서 별도로 정의한다.

- 정렬 기준 (단, 8.3장의 큐레이션 기본 원칙을 준함)

- 데이터베이스 상세 스키마
- 분석 알고리즘 세부 구현

- LLM 프롬프트 구조
- 배치 실행 주기와 세부 API 예산
- 최종 인증 제공자와 세션 관리 방식

- 다국어 지원 범위와 커뮤니티 언어 정책

### 13.1 알려진 제약 사항 (Constraints)

## 15. 시스템 정의 요약

AgentHub는 개인 개발자가 AI Agent 기술 흐름을 빠르게 따라가기 위해 사용하는 기술 탐색 커뮤니티 서비스이다.

이 시스템은 GitHub Agent 관련 repo를 수집하고, README Claim과 구현 근거를 비교하며, MCP/Skill/Tool-use/Eval/Risk 관점에서 repo를 요약한다. 또한 사용자가 팔로우업을 쉽게 시작할 수 있도록 팔로우업 가이드를 제공한다.

동시에 개발자 커뮤니티가 repo에 대한 경험, 판단, 보완 정보, 토론을 축적할 수 있게 한다. 커뮤니티 신호는 로그인 사용자가 생성하며, 자동 분석 결과와 분리되어 관리된다. 관리자는 부적절한 신호를 숨김 또는 삭제하고, 잘못된 분석 결과에 대해 숨김 처리나 재분석 요청을 수행할 수 있다.

AgentHub의 핵심은 단순 인기 순위가 아니라, **Agent 기술 흐름을 빠르게 파악하고, 실제로 무엇을 확인해야 하는지 안내하는 것**이다. MVP 단계의 구현 근거와 AI 분석 결과는 확정적 검증 결과가 아니라, 사용자가 팔로우업을 시작하기 위한 구조화된 근거 신호로 제공된다.
